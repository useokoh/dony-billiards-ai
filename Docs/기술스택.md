## 1. 한눈에 보기

```
[웹 화면]  ⇄  [백엔드 API]  ⇄  [SQLite DB + 영상 폴더]
 Next.js        NestJS
                  │ 실행 요청 ↓   ↑ 분석 결과(JSON)
              [분석 프로그램]
              Python + OpenCV
```

1. 이용자가 웹 화면에서 당구대를 위에서 촬영한 1~2시간 경기 영상을 올린다.
2. 백엔드가 영상을 폴더에 저장하고, 분석 프로그램을 별도 프로세스로 실행한다.
3. 분석 프로그램이 공 3개의 위치를 찾아 영상을 이닝과 샷으로 자동 정리하고, 샷마다 경로, 샷 영상, 실패 원인, 추천 경로를 만들어 돌려준다.
4. 백엔드가 JSON을 읽어 SQLite에 저장한다.
5. 이용자가 "몇 이닝 몇 번째 샷"을 고르면 실제 경로, 샷 영상, 실패 원인, 추천 경로를 확인한다.

> **Python을 유지하는 이유:** 공 인식에 쓰는 OpenCV는 Python 자료와 도구가 가장 풍부하다. 그래서 영상 분석만 Python으로 만들고, 웹 화면과 API는 Next.js와 NestJS로 만든다.
>
> **DB 저장은 백엔드만 맡는다:** 분석 프로그램은 JSON만 만들고 DB에 직접 쓰지 않는다. DB를 고치는 곳이 하나여서 두 언어 사이에 구조가 어긋나는 일을 줄일 수 있다.

## 2. 사용 기술과 고른 이유

| 영역 | 기술 | 역할 | 고른 이유 | 대안 |
|---|---|---|---|---|
| 프론트엔드 | **Next.js** (App Router) + **TypeScript** | 경기 목록, 리플레이, 피드백 화면 | 페이지 구조를 폴더로 관리하기 쉽고 React 기반임 | — |
| 궤적 표시 | **HTML `<video>` + `<canvas>`** | 영상 위에 궤적 겹쳐 그리기 | 브라우저 기본 기능만으로 가능 (Next.js의 클라이언트 컴포넌트에서 사용) | — |
| 백엔드 | **NestJS** + **TypeScript** | API, 영상 업로드, 분석 실행, DB 저장 | 기능을 모듈 단위로 나누기 좋고 프론트엔드와 언어가 같음 | — |
| API 문서 | **@nestjs/swagger** | API 설명·시험 페이지 | 코드에서 API 문서를 만들 수 있음 | — |
| DB 연결 | **Prisma** | 테이블 정의, DB 조회·저장 | 스키마 파일 하나로 테이블을 관리하고 TypeScript 타입을 만들어 줌 | TypeORM |
| 데이터베이스 | **SQLite** | 경기 기록과 분석 결과 저장 | 별도 서버 없이 파일 하나로 동작 | 확장 시 PostgreSQL |
| 영상 분석 | **Python 3.12 이상** + **OpenCV** + **NumPy** | 공 찾기, 투시 변환, 좌표 계산 | 영상 처리의 표준 도구, 자료가 많음 | 학습형 모델(YOLO 등)은 데이터가 쌓인 뒤 검토 |
| 영상 자르기 | **FFmpeg** | 샷별 영상 만들기 | 긴 영상에서 구간을 빠르게 잘라내는 표준 도구 | — |
| 테스트 | **pytest** / **Vitest** | 쿠션 판정 등 분석 계산 / API 검증 | pytest는 Python 대표 도구, Vitest는 현재 NestJS 기본 포함 | — |
| 버전 관리 | **Git + GitHub** | 코드 기록과 제출 | 개발 과정을 남기고 공유하기 쉬움 | — |

> 라이브러리 버전은 설치 시점의 안정 버전을 쓰고, `package-lock.json`과 `requirements.txt`로 같은 환경을 다시 만들 수 있게 한다. Node.js 버전은 Next.js·NestJS·Prisma가 모두 지원하는 LTS 버전으로 맞춘다.

## 3. 3구 공 인식 방법

### 3.1 촬영 조건

| 항목 | 기준 |
|---|---|
| 각도 | 당구대 바로 위에서 내려다보기 (비스듬하면 3.2 ① 단계의 투시 변환으로 보정) |
| 범위 | 당구대 테두리(쿠션) 4면이 모두 화면에 들어오게 |
| 고정 | 삼각대·거치대로 휴대폰 고정 (흔들리면 위치가 틀어짐) |
| 화질 | 1080p, 30fps 이상 |
| 길이 | **경기 전체 1~2시간** (개발 중 시험에는 짧은 구간을 잘라서 사용) |
| 전원·저장 공간 | 촬영이 끝날 때까지 충전 연결, 수 GB 이상의 여유 공간 확보 |
| 조명 | 촬영 중 조명 변화 없이 일정하게 |

### 3.2 처리 단계

| 단계 | 하는 일 | 방법 |
|---|---|---|
| ① 당구대 펴기 | 비스듬한 화면을 위에서 본 직사각형으로 변환 | 당구대 안쪽 모서리 4점을 처음에 한 번 지정 → OpenCV 투시 변환 |
| ② 공 찾기 | 흰공·노란공·빨간공 위치 찾기 | 색 공간을 HSV로 바꿔 색 범위로 구분 → 원 모양인지 확인 |
| ③ 위치 기록 | 프레임마다 공 3개의 좌표 저장 | 당구대 크기 기준 0~1 좌표로 저장 (영상 크기와 무관) |
| ④ 빈칸 보정 | 손·큐에 가려 못 찾은 프레임 채우기 | 앞뒤 프레임 위치로 보간, 보간한 값은 표시해 둠 |
| ⑤ 샷 나누기 | 한 번 친 샷의 시작과 끝 찾기 | 공이 움직이기 시작 → 시작, 모든 공이 멈춤 → 끝 |
| ⑥ 쿠션 판정 | 수구가 쿠션에 닿은 횟수 세기 | 공이 테두리에 가까워진 뒤 진행 방향이 바뀌면 1회 |
| ⑦ 충돌 순서 | 수구가 목적구를 맞힌 순서 찾기 | 수구와 다른 공의 거리가 공 지름보다 가까워지는 순간 |
| ⑧ 이닝 나누기 | 샷에 이닝과 순번 붙이기 | 대회 경기 방식 기준: 먼저 움직인 공으로 수구를 판별하고, 수구가 바뀌면 다음 선수의 차례로 처리. 선공과 후공이 한 번씩 차례를 마치면 1이닝 |
| ⑨ 성공·실패 판정 | 득점 여부와 실패 원인 찾기 | 쿠션 횟수와 충돌 순서를 3쿠션 규칙에 대입 |
| ⑩ 추천 경로 | 더 나았을 경로 찾기 | 샷 시작 때 공 위치에서 후보 경로를 계산해 비교 |
| ⑪ 샷 영상 | 샷별 짧은 영상 만들기 | 샷 시작 1초 전부터 공이 모두 멈춘 1초 뒤까지 FFmpeg로 잘라 저장 (최대 30초) |

### 3.3 샷 선택 시 보여주는 분석

| 항목 | 내용 | 만드는 방법 |
|---|---|---|
| 실제 경로 | 수구와 목적구가 움직인 길 | 저장한 궤적을 당구대 그림 위에 표시 |
| 샷 영상 | 그 샷만 잘라낸 영상 (공이 멈출 때까지) | ⑪ 단계의 영상 재생 |
| 실패 원인 | 실패한 샷의 이유 | 아래 표의 규칙으로 판정 |
| 추천 경로 | 그 배치에서 더 나았을 경로 | 쿠션 반사 계산으로 후보를 만들어 공을 맞히는 경로 선택 |

| 실패 원인 | 판정 조건 |
|---|---|
| 첫 목적구를 맞히지 못함 | 수구가 다른 공에 닿지 않음 |
| 두 번째 목적구를 맞히지 못함 | 목적구 하나만 맞힘 |
| 쿠션 부족 | 두 번째 목적구를 맞히기 전 쿠션이 3회 미만 |

> **추천 경로의 한계:** 영상만으로는 회전과 힘을 정확히 알기 어렵다. 그래서 시제품의 추천 경로는 "정답"이 아니라 공 배치와 쿠션 반사 계산에 따른 참고 경로로 표시한다. 회전까지 반영한 최적 경로는 이후 과제로 둔다.

### 3.4 득점 판정의 범위

3쿠션은 수구가 두 목적구를 모두 맞히기 전에 쿠션을 3회 이상 닿아야 득점이다. 이를 판정하려면 공끼리 맞았는지 정확히 알아야 하는데, 이는 쿠션 판정보다 어렵다.

- 시제품에서는 **"득점 후보"로 표시**하고, 웹 화면에서 사람이 확인(인정/불인정)할 수 있게 한다.
- 자동 득점 판정의 정확도는 실제 영상으로 검증한 뒤 높여 나간다.

## 5. 데이터베이스 설계 (SQLite)

테이블은 `api/prisma/schema.prisma`에 정의한다. 아래 자료형은 SQLite 기준이다.

### 5.1 테이블 관계

```
stores (매장)
  └─ billiard_tables (당구대)
       └─ matches (경기 = 영상 1개)
            ├─ analysis_runs (분석 실행 기록)
            ├─ innings (이닝)
            │    └─ shots (샷)
            │         ├─ shot_events (샷 안의 쿠션 접촉·공 맞힘)
            │         ├─ trajectories (궤적: 샷×공마다 좌표 배열)
            │         ├─ clips (샷별 영상, 샷당 1개)
            │         ├─ recommended_routes (추천 경로)
            │         └─ feedback (샷 피드백)
            └─ feedback (경기 전체 피드백)
```

### 5.2 테이블 상세

**stores — 매장**
| 컬럼 | 자료형 | 설명 |
|---|---|---|
| id | INTEGER PK | 매장 번호 |
| name | TEXT | 매장 이름 (시제품 단계에서는 시범 매장 1곳) |
| created_at | TEXT | 등록 시각 |

**billiard_tables — 당구대**
| 컬럼 | 자료형 | 설명 |
|---|---|---|
| id | INTEGER PK | 당구대 번호 |
| store_id | INTEGER FK → stores | 소속 매장 |
| name | TEXT | 예: "3번 대대" |
| corners | TEXT | 기본 모서리 4점 (JSON). 영상마다 다르면 `matches.corners`가 우선 |

**matches — 경기 (영상 1개)**
| 컬럼 | 자료형 | 설명 |
|---|---|---|
| id | INTEGER PK | 경기 번호 |
| table_id | INTEGER FK → billiard_tables | 경기한 당구대 |
| played_at | TEXT | 경기 일시 (영상 파일 이름의 yyMMddHHmmss에서 읽음) |
| first_player, second_player | TEXT | 선공·후공 이름 (선택 입력) |
| first_cue_ball | TEXT | 선공의 수구 `white` / `yellow` (분석 후 채움) |
| video_path | TEXT | 원본 영상 파일 위치 |
| fps, duration_sec | REAL | 프레임 번호 ↔ 초 변환용, 영상 길이 |
| corners | TEXT | 이 영상의 모서리 4점 (JSON) |
| track_path | TEXT | 전체 궤적 원본 `track.npz` 위치 |
| status | TEXT | `uploaded` → `analyzing` → `done` / `failed` |
| progress | INTEGER | 분석 진행률 (0~100) |
| error_message | TEXT | 실패 이유 |
| score_first, score_second | INTEGER | 선공·후공 득점 (사람이 확인한 샷 기준 집계) |
| created_at, updated_at | TEXT | 등록·수정 시각 |

**analysis_runs — 분석 실행 기록**
| 컬럼 | 자료형 | 설명 |
|---|---|---|
| id | INTEGER PK | |
| match_id | INTEGER FK → matches | 대상 경기 |
| step | TEXT | `detect` / `track` / `shots` / `clips` / `all` |
| status | TEXT | `queued` / `running` / `done` / `failed` |
| progress | INTEGER | 단계 진행률 |
| options | TEXT | 실행 옵션 (JSON) |
| log_path, error_message | TEXT | 로그 위치, 실패 이유 |
| started_at, finished_at, created_at | TEXT | 시작·끝·등록 시각 |

**innings — 이닝**
| 컬럼 | 자료형 | 설명 |
|---|---|---|
| id | INTEGER PK | |
| match_id | INTEGER FK → matches | 소속 경기 |
| inning_no | INTEGER | 이닝 번호 (선공·후공의 차례를 묶은 단위) |
| score_first, score_second | INTEGER | 이 이닝의 선공·후공 득점 |

**shots — 샷**
| 컬럼 | 자료형 | 설명 |
|---|---|---|
| id | INTEGER PK | 샷 번호 |
| match_id | INTEGER FK → matches | 소속 경기 |
| inning_id | INTEGER FK → innings | 소속 이닝 |
| shot_no | INTEGER | 경기 전체에서 몇 번째 샷인지 |
| shot_no_in_inning | INTEGER | 이닝 안에서 몇 번째 샷인지 |
| shot_no_in_turn | INTEGER | 한 선수의 차례 안에서 몇 번째 샷인지 (하이런 계산) |
| player | TEXT | `first` (선공) / `second` (후공) |
| cue_ball | TEXT | 수구: `white` 또는 `yellow` |
| start_frame, end_frame | INTEGER | 샷의 시작·끝 프레임 |
| start_sec, end_sec | REAL | 영상 안에서 샷의 시작·끝 시간(초) |
| rest_sec | REAL | 공이 모두 멈춘 시간(초) |
| cushion_count | INTEGER | 쿠션 횟수 |
| cushions_before_second_hit | INTEGER | 두 번째 목적구 전 쿠션 수 (3쿠션 판정 핵심값) |

### 5.3 분석 결과 가져오기

분석 프로그램이 만든 `data/results/shots/*.json`을 백엔드가 읽어 DB에 넣는다. 같은 영상을 다시 가져오면 이전 경기 기록을 지우고 새로 넣는다(경기 번호는 새로 매겨진다).

```bash
cd api
npm run import:results                                   # data/results/shots/*.json 전부
npm run import:results -- ../data/results/shots/파일.json  # 지정한 파일만
```

- 매장·당구대 등록 화면이 아직 없어서 "테스트 매장 / 1번 당구대"를 자동으로 만든다.
- fps와 영상 길이는 `ffprobe`로 읽는다. 실패하면 샷의 프레임 번호와 시간으로 fps를 추정한다.
- 궤적(`trajectories`)은 분석 결과가 `track.npz`로만 있어 아직 넣지 않는다. 분석 프로그램이 샷별 궤적 JSON을 만들면 이어서 넣는다.

## 6. 백엔드 API (NestJS)

| 방식 | 주소 | 하는 일 |
|---|---|---|
| POST | `/api/matches` | 영상 업로드 → 경기 생성 → 분석 시작 |
| GET | `/api/matches` | 경기 목록 |
| GET | `/api/matches/:id` | 경기 정보 (상태, 영상 위치) |
| GET | `/api/matches/:id/innings` | 이닝별 샷 목록 (성공·실패, 쿠션 횟수) |
| GET | `/api/shots/:id` | 샷 상세 (실패 원인, 샷 영상 위치) |
| GET | `/api/shots/:id/trajectory` | 샷의 궤적 좌표 (화면에서 그리기용) |
| GET | `/api/shots/:id/route` | 샷의 추천 경로 |
| GET | `/api/shots/:id/feedback` | 샷의 피드백 문장 |
| PATCH | `/api/shots/:id` | 득점 후보를 사람이 인정/불인정 |
| GET | `/videos/:파일` | 영상 파일 재생 (구간 이동을 위해 Range 요청 지원) |

- **분석 실행:** 업로드 후 백엔드가 Python을 별도 프로세스로 실행한다. API는 기다리지 않고 바로 응답하며, 웹 화면은 `status`와 `progress`를 주기적으로 확인한다. 1~2시간 영상은 분석이 오래 걸리므로 업로드 뒤 화면을 닫아도 계속 처리한다.
- **상태 변화:** `uploaded` → `analyzing` → `done`. Python이 오류로 끝나면 `failed`로 기록한다.
- **API 문서:** Swagger 설명 페이지를 `/docs` 주소에 둔다.

분석은 웹 업로드 없이 터미널에서도 실행할 수 있게 한다.
```bash
python -m analyzer.main data/videos/test01.mp4 --out data/results/test01.json
```

## 9. 설치와 실행 (macOS)

### 9.1 처음 한 번 설치

프로젝트 폴더는 `billiards-ai/`이며, 아래 명령은 그 안에서 실행한다.

FFmpeg:
```bash
brew install ffmpeg
```

분석 프로그램 (Python):
```bash
python3 -m venv .venv
```
```bash
source .venv/bin/activate
```
```bash
pip install -r analyzer/requirements.txt
```

백엔드:
```bash
cd api && cp .env.example .env && npm install && npx prisma migrate dev
```

프론트엔드:
```bash
cd web && npm install
```

- `.venv`는 이 프로젝트 전용 Python 공간(가상환경)이다. 컴퓨터 전체에 영향을 주지 않는다.
- `api/.env`에 DB 위치와 Python 실행 경로(`../.venv/bin/python`)를 적는다. `.env`는 Git에 올리지 않는다.

### 9.2 실행

터미널 2개를 열어 각각 실행한다.

```bash
cd api && npm run start:dev
```
```bash
cd web && npm run dev
```

브라우저에서 `http://localhost:3000` (화면)을 연다. 백엔드는 `http://localhost:4000`, API 문서는 `http://localhost:4000/docs` 이다.

- 휴대폰에서 볼 때는 같은 와이파이에서 Mac의 주소로 접속한다. 이때 프론트엔드의 백엔드 주소도 Mac 주소로 맞춘다.

### 9.3 Windows에서 실행할 경우 (참고)

| macOS | Windows |
|---|---|
| `python3 -m venv .venv` | `py -m venv .venv` |
| `source .venv/bin/activate` | `.venv\Scripts\activate` |
| 경로 `data/videos/…` | 경로 `data\videos\…` (Python 코드 안에서는 `pathlib`를 써서 둘 다 동작하게 함) |

## 11. 위험 요소와 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 조명 반사로 흰공 인식 실패 | 흰공 위치가 튐 | 색 범위 조정, 반사 적은 각도로 촬영 |
| 손·큐가 공을 가림 | 일부 프레임 위치 없음 | 앞뒤 프레임 보간, 보간 표시 |
| 공끼리 붙어 있음 | 두 공이 하나로 보임 | 색으로 먼저 구분, 크기 검사 |
| 휴대폰 흔들림 | 좌표가 틀어짐 | 삼각대 고정, 필요 시 모서리 재지정 |
| 득점 판정 오류 | 잘못된 피드백 | 시제품은 "득점 후보" + 사람 확인 |
| 분석 시간 | 1~2시간 영상은 오래 걸림 | 백그라운드 처리, 진행률 표시, 프레임 건너뛰기 검토 |
| 대용량 업로드 | 수 GB 파일 전송 실패 | 시제품은 같은 Mac 안의 파일 경로 지정도 지원 |
| 사람이 당구대를 가림 | 샷 구분·이닝 오류 | 샷 구간만 분석, 불확실한 샷은 `unknown`으로 표시 |
| 추천 경로 부정확 | 회전·힘을 반영하지 못함 | 참고 경로로 표시, 샘플 샷으로 결과 검토 |
| 언어가 2개 (TypeScript, Python) | 결과 형식이 어긋나면 저장 실패 | JSON 형식을 문서로 고정하고 저장 전에 검사 |
| 개발 범위 증가 | 1인 개발 일정 부담 | 공 인식을 먼저 검증한 뒤 웹을 만듦 |
