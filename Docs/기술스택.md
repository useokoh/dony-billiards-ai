## 1. 한눈에 보기

```
[웹 화면]  ⇄  [백엔드 API]  ⇄  [SQLite DB + 영상 폴더]
 Next.js        NestJS
                  │ 실행 요청 ↓   ↑ 분석 결과(JSON)
              [분석 프로그램]
              Python + OpenCV
```

1. 이용자가 웹 화면에서 당구대를 위에서 촬영한 1~2시간 경기 영상을 올린다.
2. 백엔드가 영상을 폴더에 저장하고, 분석 프로그램을 별도 프로세스로 실행한다.
3. 분석 프로그램이 공 3개의 위치를 찾아 영상을 이닝과 샷으로 자동 정리하고, 샷마다 경로, 샷 영상, 실패 원인, 목표 핸디에 맞는 추천 경로와 실행 코칭을 만들어 돌려준다.
4. 백엔드가 JSON을 읽어 SQLite에 저장한다.
5. 이용자가 "몇 이닝 몇 번째 샷"을 고르면 실제 경로, 샷 영상, 실패 원인, 추천 경로와 실행 코칭을 확인한다.

> **업로드 운영 원칙:** 시제품의 결과 확인 화면은 모바일 웹이다. 긴 경기 영상은 휴대폰 브라우저 직접 업로드보다 당구장 카메라·Mac·분석 장치에서 저장·업로드하는 흐름을 우선 검증한다. 휴대폰에서 대용량 영상을 직접 올리는 수요가 검증되면 앱 또는 PWA에서 백그라운드 업로드·재시도·푸시 알림을 추가한다.

> **Python을 유지하는 이유:** 공 인식에 쓰는 OpenCV는 Python 자료와 도구가 가장 풍부하다. 그래서 영상 분석만 Python으로 만들고, 웹 화면과 API는 Next.js와 NestJS로 만든다.
>
> **DB 저장은 백엔드만 맡는다:** 분석 프로그램은 JSON만 만들고 DB에 직접 쓰지 않는다. DB를 고치는 곳이 하나여서 두 언어 사이에 구조가 어긋나는 일을 줄일 수 있다.

## 2. 사용 기술과 고른 이유

| 영역 | 기술 | 역할 | 고른 이유 | 대안 |
|---|---|---|---|---|
| 프론트엔드 | **Next.js** (App Router) + **TypeScript** | 경기 목록, 리플레이, 피드백 화면 | 페이지 구조를 폴더로 관리하기 쉽고 React 기반임 | — |
| 궤적 표시 | **HTML `<video>` + `<canvas>`** | 영상 위에 궤적 겹쳐 그리기 | 브라우저 기본 기능만으로 가능 (Next.js의 클라이언트 컴포넌트에서 사용) | — |
| 백엔드 | **NestJS** + **TypeScript** | API, 영상 업로드, 분석 실행, DB 저장 | 기능을 모듈 단위로 나누기 좋고 프론트엔드와 언어가 같음 | — |
| API 문서 | **@nestjs/swagger** | API 설명·시험 페이지 | 코드에서 API 문서를 만들 수 있음 | — |
| DB 연결 | **Prisma** | 테이블 정의, DB 조회·저장 | 스키마 파일 하나로 테이블을 관리하고 TypeScript 타입을 만들어 줌 | TypeORM |
| 데이터베이스 | **SQLite** | 경기 기록과 분석 결과 저장 | 별도 서버 없이 파일 하나로 동작 | 확장 시 PostgreSQL |
| 영상 분석 | **Python 3.12 이상** + **OpenCV** + **NumPy** | 공 찾기, 투시 변환, 좌표 계산 | 영상 처리의 표준 도구, 자료가 많음 | 학습형 모델(YOLO 등)은 데이터가 쌓인 뒤 검토 |
| 영상 자르기 | **FFmpeg** | 샷별 영상 만들기 | 긴 영상에서 구간을 빠르게 잘라내는 표준 도구 | — |
| 테스트 | **pytest** / **Vitest** | 쿠션 판정 등 분석 계산 / API 검증 | pytest는 Python 대표 도구, Vitest는 현재 NestJS 기본 포함 | — |
| 버전 관리 | **Git + GitHub** | 코드 기록과 제출 | 개발 과정을 남기고 공유하기 쉬움 | — |

> 라이브러리 버전은 설치 시점의 안정 버전을 쓰고, `package-lock.json`과 `requirements.txt`로 같은 환경을 다시 만들 수 있게 한다. Node.js 버전은 Next.js·NestJS·Prisma가 모두 지원하는 LTS 버전으로 맞춘다.

## 3. 3구 공 인식 방법

### 3.1 촬영 조건

| 항목 | 기준 |
|---|---|
| 각도 | 당구대 바로 위에서 내려다보기 (비스듬하면 3.2 ① 단계의 투시 변환으로 보정) |
| 범위 | 당구대 테두리(쿠션) 4면이 모두 화면에 들어오게 |
| 고정 | 삼각대·거치대로 휴대폰 고정 (흔들리면 위치가 틀어짐) |
| 화질 | 1080p, 30fps 이상 |
| 길이 | **경기 전체 1~2시간** (개발 중 시험에는 짧은 구간을 잘라서 사용) |
| 전원·저장 공간 | 촬영이 끝날 때까지 충전 연결, 수 GB 이상의 여유 공간 확보 |
| 조명 | 촬영 중 조명 변화 없이 일정하게 |

### 3.2 처리 단계

| 단계 | 하는 일 | 방법 |
|---|---|---|
| ① 당구대 펴기 | 비스듬한 화면을 위에서 본 직사각형으로 변환 | 당구대 안쪽 모서리 4점을 처음에 한 번 지정 → OpenCV 투시 변환 |
| ② 공 찾기 | 흰공·노란공·빨간공 위치 찾기 | 색 공간을 HSV로 바꿔 색 범위로 구분 → 원 모양인지 확인 |
| ③ 위치 기록 | 프레임마다 공 3개의 좌표 저장 | 당구대 크기 기준 0~1 좌표로 저장 (영상 크기와 무관) |
| ④ 빈칸 보정 | 손·큐에 가려 못 찾은 프레임 채우기 | 앞뒤 프레임 위치로 보간, 보간한 값은 표시해 둠 |
| ⑤ 샷 나누기 | 한 번 친 샷의 시작과 끝 찾기 | 공이 움직이기 시작 → 시작, 모든 공이 멈춤 → 끝 |
| ⑥ 쿠션 판정 | 수구가 쿠션에 닿은 횟수 세기 | 공이 테두리에 가까워진 뒤 진행 방향이 바뀌면 1회 |
| ⑦ 충돌 순서 | 수구가 목적구를 맞힌 순서 찾기 | 수구와 다른 공의 거리가 공 지름보다 가까워지는 순간 |
| ⑧ 이닝 나누기 | 샷에 이닝과 순번 붙이기 | 대회 경기 방식 기준: 먼저 움직인 공으로 수구를 판별하고, 수구가 바뀌면 다음 선수의 차례로 처리. 선공과 후공이 한 번씩 차례를 마치면 1이닝 |
| ⑨ 성공·실패 판정 | 득점 여부와 실패 원인 찾기 | 쿠션 횟수와 충돌 순서를 3쿠션 규칙에 대입 |
| ⑩ 추천 경로·실행 코칭 | 목표 핸디에 맞는 더 나은 경로와 실행 방법 찾기 | 샷 시작 때 공 위치에서 후보 경로를 계산하고 난이도별로 회전 방향·당점·두께·강약을 추천 |
| ⑪ 샷 영상 | 샷별 짧은 영상 만들기 | 샷 시작 1초 전부터 공이 모두 멈춘 1초 뒤까지 FFmpeg로 잘라 저장 (최대 30초) |

### 3.3 샷 선택 시 보여주는 분석

| 항목 | 내용 | 만드는 방법 |
|---|---|---|
| 실제 경로 | 수구와 목적구가 움직인 길 | 저장한 궤적을 당구대 그림 위에 표시 |
| 샷 영상 | 그 샷만 잘라낸 영상 (공이 멈출 때까지) | ⑪ 단계의 영상 재생 |
| 실패 원인 | 실패한 샷의 이유 | 아래 표의 규칙으로 판정 |
| 추천 경로 | 그 배치에서 더 나았을 경로 | 쿠션 반사 계산으로 후보를 만들고 목표 핸디별 성공 가능성·난이도로 순위화 |
| 실행 코칭 | 그 경로를 만들기 위한 방법 | 첫 목적구 두께, 쿠션 순서·방향, 권장 회전 방향·당점·강약을 그림과 문장으로 안내 |

| 실패 원인 | 판정 조건 |
|---|---|
| 첫 목적구를 맞히지 못함 | 수구가 다른 공에 닿지 않음 |
| 두 번째 목적구를 맞히지 못함 | 목적구 하나만 맞힘 |
| 쿠션 부족 | 두 번째 목적구를 맞히기 전 쿠션이 3회 미만 |

> **추천 경로·실행 코칭의 한계:** 영상만으로 사용자가 실제로 준 회전과 힘을 정확히 알기 어렵다. 따라서 "오른쪽 회전을 썼다"처럼 실제 동작을 단정하지 않는다. 대신 공 배치와 쿠션 반사 계산을 바탕으로 "이 경로는 오른쪽 회전 계열이 유리하다"와 같은 **권장 실행값**을 제공한다. 권장값도 초기에는 참고용 가설로 표시하며, 실제 결과와 이용자 확인으로 검증한다.

### 3.4 목표 핸디별 코칭 원칙

같은 공 배치라도 목표 핸디에 따라 추천할 경로와 설명이 달라져야 한다. 목표는 규칙 위반만 알려주는 것이 아니라 실패를 다음 득점으로 바꾸는 것이다.

| 목표 핸디 | 우선 추천 | 설명 방식 |
|---|---|---|
| 초급 (목표 20 이하) | 회전 의존도가 낮고 성공 확률이 높은 기본 3쿠션 경로 | 쿠션 순서·방향, 첫 목적구 두께, 과도한 힘을 피하는 방법을 짧고 명확하게 안내 |
| 중급 (목표 21~27) | 기본 경로와 회전·두께 조절이 필요한 경로를 함께 비교 | 회전 방향·당점·두께가 짧아짐/길어짐에 미치는 이유와 반복 실패 패턴을 설명 |
| 고급 (목표 28 이상) | 득점 뒤 다음 배치까지 고려한 공격 경로 여러 개 | 기대 성공률, 난이도, 미세한 회전량·속도·입사각의 차이를 비교 |

초기 판정 엔진은 공 위치·쿠션 반사·경로 길이·충돌 각도에 따른 규칙 기반 추천으로 시작한다. 실제 회전량·힘을 정밀하게 추정하는 모델은 측면 카메라 또는 충분한 라벨 데이터가 확보된 뒤 추가한다.

**현재 구현 (2026-11-09, `api/src/coaching/`)**
- 실패 유형(첫 목적구·두 번째 목적구·쿠션 부족·원인 미상) × 난이도별 경로 틀을 고르고, 샷 시작 배치(궤적의 첫 위치)가 있으면 경로를 계산한다.
- 경로 계산: 두 번째 목적구를 쿠션 기준으로 차례로 접어 펴는 **거울 반사** 방법으로 첫 목적구 → 쿠션 3개 → 두 번째 목적구 직선을 구한다. 두 목적구 순서와 실제 쿠션 조합을 모두 시도해, 첫 목적구 뒤 꺾임이 80° 이하인 것 중 가장 짧은 경로를 고른다.
- 계산값: 경로 좌표, 먼저 맞힐 공, 꺾임 각으로 구한 두께(무회전 기준 1 − cos θ), 화면 기준 진행 방향, 진행 방향 쪽 회전(시계 → 오른쪽, 반시계 → 왼쪽). 변형 경로는 두께를 한 단계 얇게/두껍게 한다.
- 한계: 무회전·이상 반사 가정이라 신뢰도는 0.35로 표시한다. 배치상 계산할 수 없는 경로는 좌표 없이 규칙 예시로 안내한다(실제 실패 샷 107개 중 초급 1순위 경로는 79개 계산). 기대 성공률과 다음 배치 이득은 아직 계산하지 않는다.

### 3.5 득점 판정의 범위

3쿠션은 수구가 두 목적구를 모두 맞히기 전에 쿠션을 3회 이상 닿아야 득점이다. 시제품은 다음 두 증거를 결합해 득점·실패를 자동 판정한다.

1. **공 움직임 증거:** 쿠션 횟수와 충돌 순서를 3쿠션 규칙에 대입한다.
2. **차례 신호:** 다음 샷에서도 같은 선수가 친 경우 득점 후 연속 이닝일 가능성을 반영한다.

두 증거가 일치하면 신뢰도 0.95, 엇갈리면 차례 신호를 우선하되 신뢰도 0.75로 낮춘다. 영상의 마지막 샷처럼 다음 샷이 없으면 공 움직임 증거만 사용하고 신뢰도 0.6으로 표시한다. 사람의 인정·불인정 값이 있으면 언제나 자동 판정보다 우선하며, 취소하면 자동 판정으로 되돌아간다.

> 이 기준은 사람이 확인한 15개 샷에서 15/15로 일치했지만, 아직 두 경기 영상에 한정된 검증이다. 새 촬영 조건과 다른 경기 영상으로 계속 검증해야 하며, 신뢰도가 낮거나 근거가 엇갈린 샷은 화면에서 확인을 권장한다.

## 5. 데이터베이스 설계 (SQLite)

테이블은 `api/prisma/schema.prisma`에 정의한다. 아래 자료형은 SQLite 기준이다.

### 5.1 테이블 관계

```
stores (매장)
  └─ billiard_tables (당구대)
       └─ matches (경기 = 영상 1개)
            ├─ analysis_runs (분석 실행 기록)
            ├─ innings (이닝)
            │    └─ shots (샷)
            │         ├─ shot_events (샷 안의 쿠션 접촉·공 맞힘)
            │         ├─ trajectories (궤적: 샷×공마다 좌표 배열)
            │         ├─ clips (샷별 영상, 샷당 1개)
            │         ├─ recommended_routes (추천 경로)
            │         └─ feedback (샷 피드백)
            └─ feedback (경기 전체 피드백)

players (플레이어 프로필: 현재 핸디·목표 핸디·선호 난이도)
  └─ feedback (플레이어의 목표 핸디 기준으로 만든 피드백)
```

### 5.3 분석 결과 가져오기

분석 프로그램이 만든 `data/results/shots/*.json`(그리고 있으면 `data/results/trajectories/*.json`)을 백엔드가 읽어 DB에 넣는다. 같은 영상을 다시 가져오면 이전 경기 기록을 지우고 새로 넣는다(경기 번호는 새로 매겨진다). 이때 **사람이 확인한 득점 값(샷 시작 프레임 기준)과 경기에 연결한 선수는 새 기록으로 옮긴다.**

```bash
cd api
npm run import:results                                   # data/results/shots/*.json 전부
npm run import:results -- ../data/results/shots/파일.json  # 지정한 파일만
```

- 매장·당구대 등록 화면이 아직 없어서 "테스트 매장 / 1번 당구대"를 자동으로 만든다.
- fps와 영상 길이는 `ffprobe`로 읽는다. 실패하면 샷의 프레임 번호와 시간으로 fps를 추정한다.
- 궤적은 `python -m analyzer.trajectory 영상`이 만든 샷별 JSON(2프레임마다, 공이 멈출 때까지)을 넣는다. 샷 번호와 시작 프레임이 맞는 것만 넣으며, 파일이 없으면 궤적 없이 가져온다.
- 점수는 가져온 뒤 "사람 확인 > 자동 판정" 규칙으로 이닝별·경기 전체를 다시 센다.

## 6. 백엔드 API (NestJS)

| 방식 | 주소 | 하는 일 |
|---|---|---|
| POST | `/api/matches` | 영상 업로드 → 경기 생성 → 분석 시작 |
| GET | `/api/matches` | 경기 목록 |
| GET | `/api/matches/:id` | 경기 정보 (상태, 영상 위치) |
| GET | `/api/matches/:id/innings` | 이닝별 샷 목록 (성공·실패, 쿠션 횟수) |
| GET | `/api/shots/:id` | 샷 상세 (실패 원인, 샷 영상 위치) |
| GET | `/api/shots/:id/trajectory` | 샷의 궤적 좌표와 샷 시작 배치 (화면에서 그리기용) |
| GET | `/api/shots/:id/route` | 목표 핸디별 추천 경로와 실행 힌트. `?level=`·`?handicap=`·`?playerId=`, 없으면 이 샷을 친 선수의 프로필 |
| PATCH | `/api/matches/:id/players` | 선공·후공 선수 프로필 연결 (`null`이면 해제) |
| GET | `/api/shots/:id/feedback` | 샷의 피드백 문장 |
| PATCH | `/api/shots/:id` | 자동 판정을 사람이 인정/불인정/취소 (`null`이면 자동 판정 사용) |
| POST/GET/PATCH | `/api/players`, `/api/players/:id` | 플레이어의 현재·목표 핸디와 코칭 난이도 관리 |
| GET | `/api/matches/:id/video` | 경기 전체 영상 재생 (구간 이동을 위해 Range 요청 지원) |
| GET | `/api/shots/:id/clip` | 샷 영상 재생 (Range 요청 지원) |

- **영상 주소:** 파일 이름 대신 경기·샷 번호로 받는다. 서버가 DB에서 파일 위치를 찾고, `data/` 폴더 밖 파일은 보내지 않는다(`../` 경로 공격 방지, 한글 파일 이름 문제 없음). 2026-11-09 `/videos/:파일`에서 변경.

- **분석 실행:** 업로드 후 백엔드가 Python을 별도 프로세스로 실행한다. API는 기다리지 않고 바로 응답하며, 웹 화면은 `status`와 `progress`를 주기적으로 확인한다. 1~2시간 영상은 분석이 오래 걸리므로 업로드 뒤 화면을 닫아도 계속 처리한다.
- **상태 변화:** `uploaded` → `analyzing` → `done`. Python이 오류로 끝나면 `failed`로 기록한다.
- **API 문서:** Swagger 설명 페이지를 `/docs` 주소에 둔다.

분석은 웹 업로드 없이 터미널에서도 실행할 수 있게 한다.
```bash
python -m analyzer.main data/videos/test01.mp4 --out data/results/test01.json
```

- 공 색은 실제 공 색(흰·노·빨)으로 궤적을 그려 바로 구분되게 한다.

### 7.1 목표 핸디별 피드백 규칙

피드백은 실패 사실만 끝내지 않고, 추천 경로와 다음 시도의 실행 방법을 반드시 함께 제시한다. 권장 회전·당점·강약은 실제 사용값 판정이 아니라 추천값임을 화면에 표시한다.

| 상황 | 초급 (목표 20) | 중급 (목표 27) | 고급 (목표 27+) |
|---|---|---|---|
| 쿠션이 부족한 실패 | 가장 짧고 단순한 3쿠션 경로와 쿠션 순서를 제시 | 짧아진 원인을 설명하고 회전 방향·두께 조절 경로를 비교 | 복수 경로의 성공률·다음 배치까지 비교 |
| 두 번째 목적구 실패 | 목적구를 향하는 마지막 쿠션 방향과 기본 두께를 안내 | 회전·당점에 따른 길이 변화를 설명 | 미세한 입사각·속도와 다음 배치의 이득을 설명 |
| 반복 실패 | 가장 자주 실패한 한 가지 기본기부터 제안 | 실패 유형별 빈도와 교정 우선순위를 제시 | 난도 대비 성공률이 낮은 선택을 찾아 전략을 제안 |

예시: "실제 경로는 두 번째 목적구 전에 짧게 섰습니다. 목표 핸디 20에서는 장쿠션 → 단쿠션 → 장쿠션의 기본 경로를 우선 시도하세요. 1적구를 약 1/2 두께로 맞히고, 오른쪽 회전 계열로 길이를 확보하는 것이 유리합니다."

## 9. 설치와 실행 (macOS)

### 9.1 처음 한 번 설치

프로젝트 폴더는 `billiards-ai/`이며, 아래 명령은 그 안에서 실행한다.

FFmpeg:
```bash
brew install ffmpeg
```

분석 프로그램 (Python):
```bash
python3 -m venv .venv
```
```bash
source .venv/bin/activate
```
```bash
pip install -r analyzer/requirements.txt
```

백엔드:
```bash
cd api && cp .env.example .env && npm install && npx prisma migrate dev
```

프론트엔드:
```bash
cd web && npm install
```

- `.venv`는 이 프로젝트 전용 Python 공간(가상환경)이다. 컴퓨터 전체에 영향을 주지 않는다.
- `api/.env`에 DB 위치와 Python 실행 경로(`../.venv/bin/python`)를 적는다. `.env`는 Git에 올리지 않는다.

### 9.2 실행

터미널 2개를 열어 각각 실행한다.

```bash
cd api && npm run start:dev
```
```bash
cd web && npm run dev
```

브라우저에서 `http://localhost:3000` (화면)을 연다. 백엔드는 `http://localhost:4000`, API 문서는 `http://localhost:4000/docs` 이다.

- 휴대폰에서 볼 때는 같은 와이파이에서 Mac의 주소로 접속한다. 이때 프론트엔드의 백엔드 주소도 Mac 주소로 맞춘다.

### 9.3 Windows에서 실행할 경우 (참고)

| macOS | Windows |
|---|---|
| `python3 -m venv .venv` | `py -m venv .venv` |
| `source .venv/bin/activate` | `.venv\Scripts\activate` |
| 경로 `data/videos/…` | 경로 `data\videos\…` (Python 코드 안에서는 `pathlib`를 써서 둘 다 동작하게 함) |
